Capítulo 1. Un flujo de trabajo reproducible

NotaObjetivos
  • Organizar un proyecto de investigación para que otra persona (o tú dentro de un año) pueda reproducirlo.
  • Usar Git para el control de versiones y GitHub para colaborar y publicar.
  • Gestionar entornos y dependencias en Python y en R.

1. Prácticas «suficientemente buenas»

Wilson et al. (2017) proponen un conjunto mínimo de prácticas que cualquier investigador puede adoptar, aunque no sea programador profesional. Las agrupan en seis áreas:

Área Prácticas clave
Gestión de datos Guardar los datos brutos sin tocar; crear los datos analizados con código; usar formatos abiertos; dar identificadores únicos; depositar los datos con un DOI
Software Comentarios y documentación breves; descomponer en funciones; no repetir código; usar bibliotecas existentes; nombres descriptivos
Colaboración Un archivo README; una lista de tareas; una licencia; una forma acordada de comunicarse
Organización del proyecto Una carpeta por proyecto con subcarpetas estándar; nombres de archivo que indiquen contenido
Seguimiento de cambios Copias de seguridad automáticas; control de versiones; cambios pequeños y frecuentes
Manuscritos Texto en formatos que permitan seguir cambios; referencias gestionadas

Una estructura de proyecto sencilla y suficiente:

mi-proyecto/
├── README.md          qué es, cómo reproducirlo, licencia, cita
├── datos/
│   ├── brutos/        tal como llegaron (nunca se editan a mano)
│   └── procesados/    generados por el código
├── codigo/            scripts y funciones
├── resultados/        figuras y tablas generadas
├── documentos/        manuscrito (por ejemplo, en Quarto)
├── pyproject.toml     o renv.lock: dependencias
└── .gitignore         lo que no entra en Git

2. Git y GitHub

El control de versiones registra cada cambio de los archivos del proyecto, quién lo hizo y por qué, y permite volver atrás. Git es el sistema más usado; GitHub (o GitLab, Codeberg) alojan los repositorios en línea para colaborar y publicar.

Los conceptos básicos:

  • Un repositorio es la carpeta del proyecto con su historial.
  • Un commit es una instantánea de los cambios con un mensaje que explica el porqué.
  • Una rama es una línea de trabajo paralela; se integra con un merge o, en GitHub, con una pull request.
  • .gitignore indica qué no se versiona: datos personales, archivos enormes, contraseñas y claves de API, resultados que se regeneran.
1git init
2git add codigo/limpieza.py
3git commit -m "Normaliza los DOI antes de deduplicar"
4git log --oneline
5git switch -c analisis-bayes
6git push origin main
1
Crea el repositorio en la carpeta actual (una sola vez por proyecto).
2
Prepara el cambio: elige qué archivos entran en la próxima instantánea.
3
Guarda la instantánea con un mensaje que explica por qué, no qué (el qué ya lo dice el diff).
4
Muestra el historial, un commit por línea.
5
Crea una rama y se cambia a ella: aquí puedes experimentar sin tocar main.
6
Sube la rama principal a GitHub; la primera vez necesitas git remote add origin URL.

Y una conexión con el resto del libro: si enlazas el repositorio con Zenodo, cada versión publicada (release) en GitHub recibe automáticamente un DOI citable. Así se publicaron los libros de esta colección.

3. Entornos y dependencias

El código que funciona hoy puede fallar mañana porque cambió una biblioteca. Un entorno aísla las dependencias de cada proyecto, y un archivo de bloqueo registra las versiones exactas:

Python R
Crear el entorno uv init renv::init()
Añadir una dependencia uv add pandas install.packages("dplyr")
Registrar versiones uv.lock (automático) renv::snapshot() → renv.lock
Reproducir en otro ordenador uv sync renv::restore()

Ejercicios

Ejercicio 1.1 · Python

Los nombres de archivo con fechas en formato ISO 8601 (AAAA-MM-DD) se ordenan solos. Construye el nombre 2026-03-07_encuesta.csv a partir de las variables.

{dia:02d} escribe el número con dos cifras, rellenando con un cero.

anio, mes, dia = 2026, 3, 7
f"{anio}-{mes:02d}-{dia:02d}_encuesta.csv"

Ejercicio 1.2 · R

Haz lo mismo en R con sprintf().

El tercer %02d corresponde al día.

anio <- 2026; mes <- 3; dia <- 7
sprintf("%d-%02d-%02d_encuesta.csv", anio, mes, dia)

Caso práctico resuelto

NotaRescatar un proyecto desordenado

Una carpeta real de tesis: datos_final.xlsx, datos_final_v2_BUENO.xlsx, analisis.R, analisis_copia.R, grafico1.png… Plan de rescate en una tarde:

  1. Estructura: crear datos/brutos, datos/procesados, codigo, resultados; mover los originales a brutos y no tocarlos más.
  2. Identificar el script vigente comparando fechas y contenido; borrar las copias tras guardarlas en Git.
  3. Git: git init, un primer commit con todo y, a partir de ahí, cambios pequeños con mensajes claros.
  4. Un script maestro que ejecute en orden: limpieza → análisis → figuras.
  5. Entorno: renv::init() o uv init para fijar versiones.
  6. README con cómo reproducir los resultados.

Prueba final: clonar el repositorio en otra carpeta y ejecutar el script maestro sin tocar nada.

Ejercicios graduados

Básico. ¿Qué mensaje de commit es mejor: «cambios» o «Excluye cuestionarios incompletos antes del análisis»?

El segundo: explica qué cambia y por qué, y permite encontrar el cambio más tarde en el historial.

Avanzado. Aplica el plan de rescate a un proyecto tuyo y documenta en el README los pasos para reproducirlo.

El README debe indicar requisitos, cómo instalar el entorno, el orden de ejecución, qué produce cada script y la licencia de los datos y del código.
